# Accounts and Usage

EasySB replaces the old node-level credentials with a per-account model: every account has independent credentials on every protocol, with a quota, an expiry and allowed protocols. The account store `/etc/sing-box/easysb-users.json` is the only source of credentials, and the core configuration and subscription content are both derived from it.

## The account store file

The account store always lives at `/etc/sing-box/easysb-users.json`, with mode `0600`. Writes are atomic: the panel first creates a `*.tmp-*` temporary file in the target directory, then `rename`s it into place, so a half-written document cannot appear; `CreateTemp` itself is `0600`, so key material is not affected by the calling process's umask.

The file top level is a version number and an array of accounts:

```json
{
  "version": 1,
  "users": [
    {
      "name": "alice",
      "remark": "phone",
      "token": "k7m2p9q4rt3xz8",
      "enabled": true,
      "protocols": ["anytls", "hysteria2", "tuic"],
      "credentials": {
        "anytls": { "password": "Wq3vC1r9pLkZ8sTn" },
        "hysteria2": { "password": "Yb6nH2tRf4wQ1xMe" },
        "tuic": {
          "uuid": "a9a6e2b5-5e34-4899-9865-f021e27bafc3",
          "password": "Jd8kS3mZp5vLo2cB"
        }
      },
      "quota_bytes": 107374182400,
      "used_bytes": 21474836480,
      "upload_bytes": 6442450944,
      "download_bytes": 15032385536,
      "created_at": "2026-09-24T11:00:00Z",
      "expire_at": "2026-10-24T00:00:00Z",
      "last_reset": "2026-10-01T00:00:00Z",
      "applied": true
    }
  ]
}
```

The credentials above are sample values too; real accounts are generated by the panel.

## Fields

| Field | Description |
| :--- | :--- |
| `name` | Display name, used for the interface and as a prefix on client node names; at most 40 characters |
| `remark` | Remark, may be empty |
| `token` | The token in the subscription URL, and the user name used for core-side accounting; lowercase ASCII letters, digits and hyphens |
| `enabled` | Administrator switch. Turning it off disables the account and keeps credentials |
| `protocols` | Protocol keys available to this account, stored in a fixed canonical order |
| `credentials` | Credentials keyed by protocol, holding only the fields that protocol needs |
| `quota_bytes` | Traffic quota in bytes; `0` means unlimited |
| `used_bytes` | Total used, equal to upload plus download |
| `upload_bytes` | Cumulative uploaded bytes |
| `download_bytes` | Cumulative downloaded bytes |
| `created_at` | Creation time |
| `expire_at` | Expiry time; a zero value means never expires |
| `last_reset` | Start of the current traffic period, used for monthly reset |
| `applied` | Whether the account is currently written into the core configuration, used by quota enforcement to decide on a restart |

`credentials` is keyed by protocol, and the protocol keys come from `internal/state` (`state.Keys`): `vless-reality` and `vmess-ws-tls` use `uuid`, `anytls` and `hysteria2` use `password`, and `tuic` needs both.

## Derived state

State is not written to the file; it is computed at read time from the current clock, so an account regains eligibility automatically once the cause is gone. The order of judgment is:

| State | Condition |
| :--- | :--- |
| `disabled` | `enabled` is false |
| `expired` | `expire_at` is non-zero and has passed |
| `over-quota` | `quota_bytes` is greater than 0 and `used_bytes` has reached or passed it |
| `active` | None of the above |

`quota_bytes: 0` means unlimited and a zero `expire_at` means never expires; neither disables the account.

## Credential retention

Deselecting a protocol keeps its credentials in `credentials`, and re-selecting reuses the original values, so users who already imported a client are not broken by regenerated credentials. When an account is disabled, expired or over quota, the data is kept as well and recovers after a renewal or reset.

## Core-side mapping

The **core-side user name is the `token`**, not the display name. V2Ray counter keys look like `user>>><name>>>traffic>>>…`, and the name is both the aggregation key and the pattern used for `QueryStats` regex matching: a random ASCII token is unique by construction and stays stable across renames, whereas a display name may be Chinese or contain regex metacharacters.

The concrete mapping rules:

- Every enabled inbound writes one `users` record for every account that "selected this protocol, is enabled, is unexpired and is not over quota".
- When same-named accounts appear on several inbounds, accounting aggregates into the same counters.
- The `stats.users` allowlist of `experimental.v2ray_api` is rebuilt from the same decision as the inbound `users`, so only names on the list are counted.

Therefore renaming an account does not change the token, clients do not need to re-import, and accounting is not interrupted.

## Traffic accounting and reset

Usage comes from the core's `StatsService` (`experimental.v2ray_api`), sampled periodically by the accounting loop in the subscription service `easysb --serve` (every `SUB_SYNC_SECONDS` seconds, default `300`).

1. Each sample calls `QueryStats` in all-users mode with `reset=true`, then adds the delta to stored counters.
2. Counters live in the running core and go to zero when the core restarts, so what is persisted is the increment rather than an absolute value.
3. When the month of `last_reset` differs from the current month, `used_bytes`, `upload_bytes` and `download_bytes` go to zero and `last_reset` moves to this month.
4. `Reset used traffic` in the panel only zeroes the stored counters; the core-side counters are cleared by the next `QueryStats(reset=true)`.

The period is a calendar month in the host's local timezone, not a rolling N-day window, so "per month" means one month on the calendar to the reader.

## Quota and enforcement

sing-box exposes only `StatsService` and has no interface to add or remove users at runtime, so quota enforcement works by rewriting the configuration and restarting the core:

1. When an account becomes disabled, expired or over quota, it is removed from the rendered `/etc/sing-box/config.json` and `applied` is set to false.
2. The new configuration is first accepted by the `check` of the core the panel carries, then `sing-box.service` is restarted.
3. On renewal, quota reset or re-enabling, it recovers in the opposite direction.

The configuration is rewritten and restarted only on a state transition, not on every sample. The cost is a sub-second core restart at the instant an account crosses a threshold, briefly disconnecting every user on that node. The subscription service returns `403` with a plain-text reason for disabled, expired or over-quota accounts rather than a half-built configuration with no nodes; see [Subscription](/en/features/subscription) for the details.

## Managing in the panel

The account lifecycle is handled by the `Accounts and traffic` entry on the main menu, while client-facing subscription operations stay under `Subscription management`. The split:

| Entry | Handles |
| :--- | :--- |
| `Accounts and traffic` | Account list, create, name / remark / quota / expiry / allowed protocols / enable, reset used traffic, rotate token, delete |
| `Subscription management` | Subscription URL prefix, installing / restarting / checking the subscription service unit, and viewing one account's subscription |

Each account under `Accounts and traffic` has its own submenu showing the account's subscription URL, QR codes for each client format and per-protocol share links. Rotating the token immediately invalidates the old subscription URL but does not change the credentials already handed out; revoking access means disabling or deleting the account. Renaming leaves the token and accounting untouched.
